# Delivered from root_manager — the ninth class: a manager that reported was replaced, not woken

## 9. Every follow-up was a cold start, and the cold start re-read the project

- **Rule in play:** the portfolio's contract (`{project}`'s manager carries its roadmap; root learns a project by asking it), plus `resources_are_limited.economy` on where effort is placed. No rule names who starts a manager or how a second instruction reaches one.
- **Executable as written:** not applicable — nothing was written. Root_manager's own habit was: file the message into the project's mailbox, then dispatch a **new** manager for the project. The person's question, 2026-10-23: "why each time you write mail and start a manager, like is the old one even dead? Isn't the usual workflow be you start all managers, and you send them message since they're alive, just sleeping?"
- **Measured, not argued:** the previous manager does end — a dispatched child is a process with a wall-clock budget and it exits when it reports. But its session is retained and resumable by run id, and root_manager never once resumed one: every follow-up in a whole day was a cold child that re-read the project from the filesystem before it could act. Ten such starts, each 30–120k tokens of reading a project root_manager had already been told the answer to, and each losing what the previous child had learned.
- **Why it happened:** the mailbox is durable and the child is not, so root_manager treated the mailbox as the only channel and a start as the only delivery. The mechanism it missed is the one the person described: the child is asleep, not gone.
- **What root_manager makes of it:** this is the single largest avoidable cost of the day and it is a *rule* defect, not a taste one: a message filed to a project has two possible deliveries — wake the manager that already holds the project in its head, or start a fresh one — and nothing in the law says which, so the expensive one became the habit. It is also why mail and dispatch doubled: the same instruction existed twice, once as a record and once as a prompt.
- **Suggestion:** say which delivery a message takes. A manager that has reported is resumed with the message; a new manager is started only when there is none, when the earlier one is not resumable, or when its context is stale enough that re-reading is the point — and the reason is written where the dispatch is recorded. Mail stays the record; the resume is the delivery.
