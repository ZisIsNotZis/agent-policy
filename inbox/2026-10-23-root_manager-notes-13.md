# Delivered from root_manager — the seventeenth class: a probe child was spawned to answer a question about root_manager's own tooling

## 17. Root_manager spawned workers to test its own configuration

- **Rule in play:** `hierarchy` (a manager holds a directory and answers for it; a worker executes exactly one work package in its parent's area), `resources_are_limited.economy.allocate`, and the authority split in `reasoning.authority` (technique is the agent's, but doing a layer's work is not how root_manager decides a technique question).
- **The incident:** to check whether a `timeoutMs` change had taken effect, root_manager launched two `worker` children whose only task was `sleep 5` and print a number, then read their `status.json` for the resolved deadline. The person: "Wait, why are you spawning worker? That don't make sense, you don't have anything to directly work on, so no way you should spawn worker?"
- **Why it happened:** root_manager needed an observable that only a child produces (the resolved `timeoutMs` at launch), and a child is one call away. The cheapest-looking way to answer a question about root_manager's own harness was to create work that does not exist, and to fill the only role that executes a package — a role that is defined by having a parent with an area to work in. Root_manager has no area; the two children did nothing, and "work" was invented to observe a number.
- **What root_manager makes of it:** this is not a cost defect, it is a category error with a cost — the same shape as class 2 (root_manager doing a lower layer's craft) in the opposite direction: there, root_manager wrote where a writer belonged; here, root_manager manufactured a package where there was no work. Both come from treating the nearest available tool as the answer to a question about root_manager's own machinery, and both are invisible in a tree whose only artefact is "a child ran".
- **Suggestion:** two lines.
  1. **A probe is not work.** A role is spawned for a package that some holder owns; a question about root_manager's own tooling is answered by reading the configuration, by the next real launch (whose status carries the resolved value anyway), or by a local command — never by a child that exists to be measured.
  2. **The observability rule that makes it unnecessary:** whatever root_manager must know about a launch is available in the launch's own record after the fact. If a value can only be learned by spawning something, that is a gap in the record to report, not a licence to invent a package.
- **Related:** classes 2 and 9. All three are root_manager reaching for a tool that belongs to a layer beneath it; the surrounding three (7, 16, and this) are all "the receiver's surface is not the sender's".
